<a id="v5-states"></a>
### 로딩·오류·빈 상태

- 목록에 기록이 없는 경우와 필터에 맞는 기록이 없는 경우에 공통 빈 상태를 확인했습니다. 삭제된 기록의 상세·수정 화면에도 별도의 빈 상태가 표시됐습니다.
- 테스트 브라우저에서 상세 조회 응답만 오류로 바꿨을 때 오류 패널을 확인했습니다. 오류 주입을 해제하고 ‘다시 시도’를 눌러 원격 상세 데이터가 나타났습니다.
- 공통 로딩 UI의 문구는 [Vitest 테스트](../tests/ui-states.test.tsx#L8)로 확인했습니다. 이 테스트 결과를 운영 DB 장애 확인으로 간주하지 않습니다.

<a id="v5-browser"></a>
### 화면 반응과 접근성

- 감정과 검색어를 바꾸면 카드 목록이 갱신됐고, 이 조작 중 Supabase 목록 재요청은 0건이었습니다. 감정 선택 버튼의 `aria-pressed` 값과 Gooey 표시 영역도 확인했습니다.
- 헤더에서 바꾼 테마가 프로필 이동 후 유지됐습니다. 목록과 상세 사이에서 브라우저 뒤로·앞으로 이동을 확인했습니다.
- 320px 너비에서 가로 넘침이 없고 키보드 Tab으로 포커스 표시가 나타났습니다. 동작 줄이기에서는 페이지 진입 애니메이션과 Gooey 장식 표시가 해제됐습니다.
- 메모이제이션 적용 여부는 코드에서 확인했습니다. 렌더링 시간과 실기기 Safari 성능은 별도로 측정하지 않았습니다.

<a id="v5-auth"></a>
### 인증과 데이터 소유권

- 공개 브라우저에서 세션 없는 사용자의 목록 접근이 로그인으로 이어지고, 테스트 이메일 계정으로 로그인한 뒤 원격 CRUD가 동작하는 것을 확인했습니다.
- [Supabase Auth 분기](../screens/login-screen.tsx#L50)에 이메일 로그인·회원가입·익명 체험이 있습니다. 공개 v5 브라우저 검증은 이메일 계정 경로로 진행했습니다.
- [RLS 정책](../supabase/migrations/20260904203000_create_flow_entries.sql#L38)의 SELECT·INSERT·UPDATE·DELETE 조건을 확인했습니다. 이 회차에서는 두 계정 간 데이터 차단을 별도 브라우저 시나리오로 재실행하지 않았습니다.

## 삭제와 오류 상태 근거

- 삭제 쿼리는 사용자 RLS 정책 아래에서 동작하며, 원격 자동 검증에서 실제 행을 생성한 뒤 삭제하고 재조회 결과 0건까지 확인했습니다.
- 상세 화면의 삭제 버튼은 실수 방지를 위해 확인 다이얼로그를 거친 뒤 삭제합니다.
- 오류 UI는 `ErrorState` 재사용 컴포넌트로 구현했고, 재시도 클릭이 전달되는지 UI 테스트로 확인했습니다.
- 운영 DB 장애를 의도적으로 만들지 않기 위해 브라우저에서는 강제 장애를 주입하지 않았으며, 실제 원격 성공 경로와 격리된 오류 UI 테스트를 분리했습니다.
